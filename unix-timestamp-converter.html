Seconds, milliseconds and system timestamps

Unix time represents an instant as the number of elapsed seconds from the Unix epoch, while many JavaScript and API systems use milliseconds. This difference is why a timestamp can look unexpectedly large when a millisecond value is mistaken for seconds, or produce a date far in the past when the reverse mistake is made.

When investigating logs, first identify the source system and the unit it documents. The converter is useful for turning that raw value into readable local time, UTC and ISO output so you can compare an event across services. Keeping both the original timestamp and the interpreted date in your notes makes debugging easier.

UTC and local time are different views of the same instant

UTC provides a stable reference for comparing distributed systems. Local time is more convenient for a person reading a log, but it depends on the viewer's timezone and can become confusing around seasonal clock changes. Use UTC or ISO timestamps for cross-system records, then translate to local time when presenting an event to a human.

A timestamp conversion does not prove that an application recorded the correct event. It only transforms the numeric representation. If an API uses a documented custom epoch, rounds values or stores a date in another field, follow that system's specification instead of assuming every integer is Unix time.
