Why choose NexusNova HumanProof?

Use the control that matches the question you need answered.

HumanProof is not a replacement for every login or identity control. Its narrower purpose is to add evidence that a live human consciously approved one precisely described action.

Password

Evidence that someone knows a reusable secret. It does not show live presence or what action the person intended to approve.

OTP

Evidence of access to a phone, email inbox or authenticator. Malware, forwarding or social engineering can separate that code from the action shown to the user.

CAPTCHA

A bot-abuse filter for a web interaction. It is not an approval record and normally does not bind a human decision to a specific high-risk operation.

Face match

A comparison between a face and a reference image. It addresses identity similarity, not whether the person understood and approved the exact action now being requested.

NexusNova HumanProof

Combines a live-human response with conscious approval of the displayed action and an action-bound receipt architecture. It does not establish legal identity.

ACTION BINDING

Hash the exact request

A production integration should bind a nonce and stable action reference—including the material amount, destination or operation—to the approval. Any material change requires a new approval.

PRIVACY FIRST

Collect only what the proof needs

The current browser interaction performs face-landmark analysis on the device. A production deployment should document retention, minimize biometric data, and avoid presenting liveness as legal identity.

SERVER CONFIRMED

Issue only after trusted checks

The browser animation alone cannot issue a result. A production receipt must follow the paid flow, server validation and backend signing; failed, abandoned or altered requests remain unverified.

Realistic limitation

No liveness check is 100% secure or automatically deepfake-proof. Camera quality, accessibility needs, presentation attacks, compromised devices and implementation mistakes can affect results. HumanProof should be one risk-control layer alongside replay protection, rate limits, device or passkey signals, monitoring and human escalation.

Security & privacy

Keep the complexity behind a simple user flow.

The live browser interaction uses on-device face landmark analysis. A hardened production system needs additional replay resistance, device or passkey proof, nonce handling, action hashes, backend-signed receipts, abuse controls, monitoring and independent security review.

Short camera interaction

The interface is designed around brief live verification moments rather than long recording sessions.

Replay-aware architecture

Randomized challenges, timing checks, nonce binding and device signals form part of the security direction.

Action-specific proof

The goal is not only “a human was present,” but “a human approved this exact action.”

No identity claim by default

HumanProof is positioned around presence and conscious approval, not automatic real-world identity claims.

FAQ

HumanProof, explained simply.

Is HumanProof face recognition?

No. The product concept is to prove that a live human consciously approved a specific action. It does not need to identify that person by name.

Does the public flow equal production-grade liveness?

No. It is a live browser interaction and evaluation surface. Production security requires stronger anti-replay and anti-injection controls, backend verification logic, monitoring and independent security review.

Can a business integrate HumanProof without a separate app?

Yes. The commercial integration direction is verification links, an embedded web SDK/widget and a REST API.

Is production verification free?

No. The business model is paid production verification. Public evaluation can be used to understand the interaction without receiving a production receipt.

Does HumanProof move or hold money?

No. HumanProof is designed as an approval and verification layer. A bank, wallet, marketplace or app remains responsible for the underlying transaction.
